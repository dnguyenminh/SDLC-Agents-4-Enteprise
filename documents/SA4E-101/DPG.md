## 1. Overview

### 1.1 Feature Summary

SA4E-101 makes the code-intel index progress state **persistent and multi-tenant**. The
indexing engine now records each operation in a `index_operations` table (hot in-memory +
cold DB dual-path) and persists file checksums per tenant in `file_checksums`. On backend
restart, stale `running` records are auto-detected and marked `interrupted` (so the
extension stops showing a permanently-spinning progress bar), and an interrupted operation
can be re-surfaced from DB. A periodic `CleanupScheduler` removes terminal records older
than 1 hour. The feature degrades gracefully (EF-04): if the DB is unavailable at boot, the
server still starts and progress simply does not survive restart.

### 1.2 Deployment Scope

| Item | Type | Description |
|------|------|-------------|
| Schema bootstrap | New (idempotent DDL) | `ensureSa4e101Tables()` creates `index_operations` + `file_checksums` tables and indexes at server boot |
| Startup interrupt detection | New (internal) | `runStartupInterruptDetection()` marks stale `running` → `interrupted` before accepting HTTP traffic |
| Cleanup scheduler | New (internal) | `CleanupScheduler` deletes terminal records older than 1h every 10 min |
| Index operation manager | New (internal) | `IndexOperationManager` tracks active ops per `(user_id, project_id)` with auto-cancel-and-replace |
| Checksum service | New (internal) | `ChecksumService` persists/loads per-tenant checksums for skip-optimization |

## 4. Database Migration

### 4.1 Migration Scripts

| Order | Script | Description | Estimated Time |
|-------|--------|-------------|----------------|
| 1 | (inline, idempotent) | `ensureSa4e101Tables()` DDL executed at server boot — **no separate .sql file to run** | < 1s |

The DDL is engine-aware (SQLite vs PostgreSQL `TIMESTAMP` type) and safe to run on every
boot (`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`).

### 4.2 Execution Steps

Schema creation is **automatic** — no manual step required. To verify it ran:

```bash
# 1) Deploy the new backend build and start it
npm run start          # or: npx tsx src/index.ts

# 2) Confirm the tables exist (SQLite example)
sqlite3 <db-file> ".tables" | tr ' ' '\n' | grep -E 'index_operations|file_checksums'

# 3) Confirm indexes exist
sqlite3 <db-file> "SELECT name FROM sqlite_master WHERE type='index' AND name LIKE '%operations%';"
```

### 4.3 Verification Queries

```sql
-- SQLite / PostgreSQL: tables present
SELECT name FROM sqlite_master WHERE type='table'
  AND name IN ('index_operations','file_checksums');

-- PostgreSQL equivalent
SELECT tablename FROM pg_tables WHERE tablename IN ('index_operations','file_checksums');

-- Partial unique index enforces at most ONE active (running/interrupted) op per tenant
SELECT count(*) FROM index_operations WHERE status IN ('running','interrupted');
```

### 4.4 Rollback Scripts

```sql
-- Rollback: drop the two SA4E-101 tables (also requires reverting the deployed build)
DROP TABLE IF EXISTS file_checksums;
DROP TABLE IF EXISTS index_operations;
```

> Note: dropping the tables without reverting the code will cause the next boot's
> `ensureSa4e101Tables()` to recreate them (idempotent). For a true rollback, revert the
> build AND drop the tables.

## 5. Application Deployment

### 5.1 Deployment Flow

Startup sequence (wired in `HttpServer.start()`, non-blocking):

```
listen() ─▶ ensureSa4e101Tables()
                └▶ runStartupInterruptDetection()   (stale running → interrupted)
                      └▶ new CleanupScheduler().start()  (every 10 min GC)
```

### 5.2 Deployment Steps

| Step | Action | Command | Verification |
|------|--------|---------|-------------|
| 1 | Stop existing service | `pkill -f "tsx src/index.ts"` (or stop container) | process stopped |
| 2 | Deploy new artifact | copy build / `git checkout <release>` | files in place |
| 3 | Start service | `npm run start` | process up |
| 4 | Health check | `GET /health` (or server log) | 200 OK / "Backend server started" |
| 5 | Verify SA4E-101 init | inspect logs (see 7.3) | tables ensured + scheduler started |

### 5.3 Docker Deployment (if applicable)

```bash
docker pull {registry}/code-intel-backend:{tag}
docker stop code-intel-backend
docker run -d --name code-intel-backend -p 48721:48721 \
  -e CODE_INTEL_WORKSPACE=/data {registry}/code-intel-backend:{tag}
docker logs code-intel-backend --tail 50
```

### 7.2 Smoke Tests

| # | Scenario | Steps | Expected Result |
|---|----------|-------|-----------------|
| 1 | Restart survives progress | Start index, kill backend, restart | stale `running` row becomes `interrupted` (log: `[startup-interrupt] marked stale running operations as interrupted`) |
| 2 | Terminal GC | Insert a `completed` row with `updated_at` > 1h old, wait 10 min | row removed by `CleanupScheduler` |
| 3 | Tenant isolation | Two tenants index concurrently | each sees only its own operation (partial unique index) |

### 7.3 Log Verification

| Log Entry | Level | Expected | Location |

## 8. Rollback Plan

### 8.1 Rollback Flow

Revert build → drop SA4E-101 tables (4.4) → restart.

### 8.2 Rollback Decision Criteria

| Condition | Action |
|-----------|--------|
| Critical defect in persistence init blocking startup | Immediate rollback |
| Data-integrity issue with `index_operations` | Immediate rollback + DBA investigation |
| Minor issue (e.g., cosmetic progress glitch) | Hotfix — no rollback |

### 8.3 Rollback Steps

| Step | Action | Command | Verification |
|------|--------|---------|-------------|
| 1 | Stop new version | `pkill -f "tsx src/index.ts"` | stopped |
| 2 | Revert build | `git checkout <prev-release>` | files reverted |
| 3 | Drop SA4E-101 tables | run 4.4 SQL | tables gone |
| 4 | Start previous version | `npm run start` | healthy |
| 5 | Verify rollback | `GET /health` | 200 OK |

### 8.4 Rollback Time Estimate

| Action | Estimated Time |
|--------|---------------|
| Application rollback | 2 min |
| Database rollback (drop 2 tables) | < 1 min |
| Verification | 2 min |
| **Total** | **~5 min** |
